# Steering target state and feedback acceptance — 0.6.1

The vehicle panel previously displayed the phone's supervisor output (`0°` for STOP), while the tuning panel displayed the ESP32's stored `targetAngle`. STOP disabled motor output but did not clear that stored angle; ARM also filled it with the current wheel angle. An inactive controller could therefore display a 12° “target” indefinitely. A zero output within the configured deadband could look similar.

The firmware now clears the target and revokes its lease on STOP, fault, expiry and arming. The tuning reply includes a signed `pid_active` flag derived from actual arming, fault, feedback and command-lease state. The UI displays **PID inactive / No applied target** when appropriate, and plots the blue target only during active control. Missing or expired readings do not remain labelled as live feedback. The vehicle panel labels its second angle **phone request**; the tuning panel labels its active angle **ESP target**. These independently sampled paths can still differ briefly while a new request is in transit.

STOP continues to switch off steering output; it does not drive the wheels toward center. A stopped car can remain physically turned. A fresh manual command with a 0° steering request activates centering under the existing command lease.

Feedback acceptance is now at least **−60° to +60°**, compared with −29° to +29° on this car before the change. This is a measurement plausibility window, not a larger commanded travel range. Commands remain limited to the calibrated **−26° to +26°**, and outward effort at those endpoints is still cut. An overshot wheel can be driven inward without first latching a range fault. Angles beyond the calibrated endpoints are extrapolated and labelled accordingly in the console.

Each feedback update uses the median of three ADC samples. A rejected feedback sample immediately neutralizes motor outputs and cancels the old target, but a brief glitch does not latch a whole-system fault. Continuously invalid feedback for 50 ms still raises `STEERING_FEEDBACK`. ADC rails and non-finite/grossly implausible values remain invalid. The tuning panel reports feedback validity, accepted range and rejected-sample count.

Protocol diagnostics version 2 signs the activity flag, feedback validity, acceptance range, rejection count and calibrated command bounds. The host remains compatible with the earlier settings protocol, but marks activity as unreported rather than inventing an active target on older firmware. No APK change is needed.

Software checks cover retained-target clearing, arming without an inherited target, overshot feedback with inward-only recovery, transient invalid feedback neutralization, persistent feedback faulting, activity/expiry flags, authenticated diagnostics, stale UI readings and legacy replies. Hardware installation requires the ESP32's USB serial connection. Capture active settings before resetting/flashing, and restore any temporary gains afterward using `verify_steering_storage.py --snapshot PATH` and `--restore PATH`.

No arm/motion commands were sent; physical steering under load remains an operator test.
